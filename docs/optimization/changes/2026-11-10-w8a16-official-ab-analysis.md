# 沐曦 W8A16 四投影官方双场景对照与初步归因

## 1. 基本信息与摘要
2026-11-10，MetaX C500，128 GiB 主机内存。本次不修改生产源码，归档现有四投影三算法候选与 BF16 的正式对照。量化权重为静态对称 per-output-channel INT8、FP32 scale，激活 BF16，INT8 转 BF16 参与 dot、FP32 累加；不是原生 INT8 GEMM。两套各场景四轮，跳过首轮取后三轮平均；16 轮请求全部成功。模型精度未执行。

## 2. 问题与原因分析
性能退化在计入平均的重复轮次中持续存在，不是只由首次编译导致。候选四类投影共168个，相比历史Down-only的42个扩大覆盖，因此历史约5%的Down-only损失不可直接外推。

大M的Separate每次调用转换全部INT8权重为BF16，调用原生MM，再执行独立scale，无持久转换权重；访存、输出中间张量和额外启动开销都会进入计时。Prefill中权重转换相对MM的比例可能下降，但输出scale的开销随M增加，不能简单假定大M免费。小M分发还增加Split-K partial/workspace/reduce或Dense路径。候选的数学形式并不保证比BF16快。

M64的静态分发为Down/QKV/O使用Split-K，GateUp使用Dense；大M范围外为Separate。此处仅说明代码策略，实际M、算法调用次数、CUDA Graph replay和各Kernel耗时占比尚无trace，不能将并发64当成真实M，也不能认定某算法为唯一原因。

运行日志证实两套均有decode FULL图捕获；没有ERROR及W8A16 fallback记录。候选KV容量1,251,152 tokens，基线1,205,696 tokens，未显示候选容量更小。以上仅排除明显现象，不等于证明没有图回放问题或资源竞争。未连续记录硬件时钟/功耗，不能断言无外部扰动。

## 3. 本次执行方式
基线使用镜像原安装插件/FlagGems，候选复制相同安装包到独立overlay，仅覆盖插件初始化、W8A16目录、MetaX weight_int8pack_mm与manifest。原生BF16 MM文件未替换。官方服务参数及Benchmark原样执行，RUNS=4、SKIP_FIRST=1不变。量化覆盖168/168；独立M64四类投影算子相对L2约0.00165，门槛0.005均通过，这不是模型精度。

## 6. 合规性与风险、后续诊断
正式测评已结束，未修改官方命令、数据和统计逻辑。当前证据只能定位为四投影完整调用成本与分发策略的联合问题，不能量化归因。建议先做现有诊断入口的同机分组完整调用比较：三算法对BF16，包含实际观测M；再比较四投影全Separate与当前分发，最后Down-only作为范围消融。需要的诊断代码变更先讨论计划，不在本次归档中实施。避免先重写Kernel或直接认定Attention/调度问题。
